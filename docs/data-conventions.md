# 資料慣例

建檔時的判斷準則。程式無法強制這些規則，但資料的一致性靠它們維持。畫面的規範另見 [ui-conventions.md](ui-conventions.md)。

## 日期

### 格式：EDTF

所有出版相關日期使用 **EDTF（ISO 8601-2）** 字串，而非日曆日期。理由是雜誌的出版時間經常只知道到月、到年、甚至只知道季節；若存成日期欄位，就必須捏造一個「日」，之後便無法與真正確知的日期區分。

| 已知程度 | 寫法 | 範例 |
| --- | --- | --- |
| 確知日期 | `YYYY-MM-DD` | `1989-04-08` |
| 只知年月 | `YYYY-MM` | `1999-05` |
| 只知年份 | `YYYY` | `1994` |
| 只知季節 | `YYYY-2X` | `1994-22`（22 夏） |
| 來源存疑 | 加 `?` | `1999-05?` |
| 大約前後 | 加 `~` | `1999-05~` |

季節代碼：`21` 春、`22` 夏、`23` 秋、`24` 冬。

**不要用 `1999-05-01` 表示「1999 年 5 月的某一天」**，那個寫法專指 5 月 1 日。

實作見 [`src/lib/edtf.ts`](../src/lib/edtf.ts)。排序不能直接比較 EDTF 字串，因此 `Magazine.foundedSort` 存放該值涵蓋區間的起點，於寫入時自動推導。

> 已知落差：`edtf.js` 把 `21`–`24` 推導成季度（`22` → 4–6 月），而規範定義為季節。字串本身符合規範，只有推導出的區間偏移。目前排序未依賴季節精度的資料，若日後有需要須重新檢視。

### 時間戳存 UTC，顯示台北時間

`createdAt`、`processedAt`、`tocReviewedAt` 這類**時刻**（不是上面說的出版日期）一律以 UTC 儲存，畫面上一律以台北時間（UTC+8）呈現。

顯示請用 [`src/lib/datetime.ts`](../src/lib/datetime.ts) 的 `formatTaipei()`，**不要直接用 `date-fns` 的 `format()`**。後者跟隨執行環境的時區，而那不是一個時區是兩個：server component 跑在 Vercel function 裡（沒設 `TZ`，所以是 UTC），client component 跑在讀者的瀏覽器裡（這裡是 UTC+8）。同一筆編輯因此在 `/admin/edit-logs` 顯示 03:20、在 `/admin/users` 顯示 11:20，台北時間早上 8 點前連日期都會差一天。

時區寫在程式碼裡而不是設在部署環境的 `TZ`，是為了讓本機、preview 與 production 一致，不會因為換平台或漏設變數又飄掉。

### 創刊日期以創刊號為準

`Magazine.foundedDate` 記錄 **創刊號** 的出版日期，**不是試刊號**。

有些雜誌在正式創刊前發行過一至數期試刊號。例如《軟體世界雜誌》1989-03-08 試刊、1989-04-08 創刊，`foundedDate` 取 `1989-04-08`。

理由是「創刊」在期刊學上有明確定義，跨雜誌比較時才有一致的基準；試刊號的數量與性質各家不一，有些甚至未對外發行。試刊號本身仍應建為 `Issue`，其出版日期記在該期數上。

## 單值欄位

### 歷史值取創刊時的版本

`Magazine.publisher` 這類**單一字串**欄位，遇到雜誌存續期間換過值時，一律填**創刊時**的值，不是最後一個值。

理由有三。其一是與 `foundedDate` 以創刊號為準一致：雜誌的識別資料都錨定在創刊那個時間點，若出版社取最新值、日期取創刊值，同一筆資料就會混著兩個時間切面。其二是查證難易：創刊號的版權頁通常查得到，中途換手往往沒有明確公告，末期尤其是停刊前的資料最難確認，取最後值等於把欄位建立在最不可靠的來源上。其三是讀者的記憶：一本雜誌讓人記住的多半是它創刊、發行量最大的那段時期，用創刊時的出版社去搜尋比較容易命中。

變動歷史記在 `description`，寫成「某時間（或某期）出版社由 A 改為 B」即可，不必展開來由。例如《電遊人》創刊時屬華彩軟體，2001 年 11 月前後獨立為富利恒，`publisher` 填「華彩軟體」，`description` 記下這次變動。

同一原則適用於其他單值欄位；雜誌**改名**則另有 `aliases` 可放，不受此節限制。

## 期號

期號（`Issue.issueNumber`）照實登錄，**不重新編號**。

早期台灣雜誌有未經授權翻譯外國雜誌的情況，會直接沿用原刊的期號，因此首期未必是第 1 期：

- 《華泰任天堂秘笈》首期即第 5 期，沿用所翻譯之日本雜誌期號
- 《電腦遊戲世界》首期即第 85 期，沿用所翻譯之美國雜誌期號

排序不依賴期號的數值，而是 `Issue.order`。

## ISSN

`Magazine.issn` **不具唯一性**，不要假設一組 ISSN 只對應一本雜誌。

雜誌改名時，出版社可能沿用同一組刊號。《電擊王》與《電玩通》皆使用 `1561-8099`。查詢時請用 `findFirst` 而非 `findUnique`。

## 描述文字

`Magazine.description` 等描述欄位以**純文字**渲染，不經過 markdown 處理。

期刊名稱請用中文書名號 `《》`，不要用 `_斜體_` 或 `*粗體*` —— 那些符號會原樣顯示。

## 遊戲封面

`Game.coverImage` 要的是**能認出「就是這一款」的辨識圖**，優先序如下：

1. **盒裝圖**（實體包裝正面）
2. **宣傳圖**（海報、廣告主視覺）
3. **遊戲標題畫面**（開場 title screen 的截圖）

理由是這個站的用途是雜誌索引：讀者是在「找回當年那本雜誌裡的那款遊戲」，而盒裝是那個年代辨識度最高的載體——在店頭看到的、在雜誌廣告上看到的都是它。宣傳圖次之，因為同一款遊戲的宣傳圖可能有很多張，未必是讀者記得的那一張。標題畫面墊底，它能確認遊戲身分但視覺辨識度最低。

**遊戲內截圖與美術設定圖不算封面**，不要拿來填這個欄位。RAWG 這類 API 給的 `background_image` 屬於這一類，即使比對到正確的遊戲，圖的種類也是錯的。

## 目錄複查

`Issue.tocReviewedAt` 記錄**有人確認過目錄內容**的時間，`null` 代表尚未複查。

會寫入這個欄位的只有帶 session 的後台操作（單期編輯表單的「目錄已人工複查」）。帶 `Authorization: Bearer` 的腳本寫入即使送出 `tocReviewed: true` 也會被忽略——機器沒有看過掃描圖，不能自稱複查過。

因此「有目錄圖但 `tocReviewedAt` 為 null」就是待人工檢查的清單，後台 `/admin/issues` 依此篩選。
